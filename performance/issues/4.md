## Problem und Nutzerziel

Der Viewer lädt derzeit für jedes Benchmark-Profil den vollständigen Benchmark: 7.003.824 Byte JSON bzw. 1.388.301 Byte gzip im Messdatensatz. Der optimierte mobile Kaltstart benötigt noch 5,82 s. Ziel: nur die Daten des gewählten Profils übertragen; beim Zurückwechseln bereits geladene Daten sofort wiederverwenden.

## Bereits gemessenes Potenzial

Ein Transferexperiment teilte die echten Daten nach Template auf und rekonstruierte den ursprünglichen Inhalt verlustfrei:

| Profil | gzip-Teilpayload | Gegenüber vollständigem Benchmark |
|---|---:|---:|
| KM1 / Headroom / Liquidität | 593.698 Byte | −57,2 % |
| Risiko | 846.950 Byte | −39,0 % |
| NPL | 65.405 Byte | −95,3 % |
| Kreditkette | 134.415 Byte | −90,3 % |
| ESG | 299.366 Byte | −78,4 % |
| Vergütung | 63.164 Byte | −95,5 % |

Das sind Payload-Größen, keine gemessenen End-to-End-Zeitgewinne. Zusätzliche Requests und Brotli können die Bilanz verändern.

## Umsetzung

- Benötigte Templates aus Profil, Kennzahlen, Querverweisen, Gates und Zeitreihenbedarf vollständig bestimmen.
- Kleine versionsgebundene Manifestdatei und Template-Dateien erzeugen; alle Ressourcen einer Ansicht müssen zur selben Datenversion gehören.
- Daten je Version/Template wiederverwenden und gleichzeitige Requests zusammenfassen.
- Schnelle Profilwechsel, Deep Links, Fehler/Wiederholen und CDN-Fallback korrekt behandeln; alte Antworten dürfen das aktive Profil nicht überschreiben.
- Veröffentlichungsreihenfolge und Rollback im vorhandenen Pages-/Datenworkflow berücksichtigen.

## Abnahme

- [ ] Verlustfreie Rekonstruktion des bisherigen Benchmarks aus Teil-Dateien nachgewiesen.
- [ ] Alle acht Profile liefern gleiche Zeilen, Kennzahlen, Perzentile, Filterresultate und Exporte; insbesondere Mehrfach-Template-Profile testen.
- [ ] KM1 benötigt bei diesem Datenstand ungefähr höchstens 600 kB gzip Benchmark-Payload; tatsächliche Request- und Brotli-Bilanz separat dokumentieren.
- [ ] Rückwechsel auf ein schon geladenes Profil derselben Version fordert dessen Daten nicht erneut an.
- [ ] Keine gemischten Versionen bei Veröffentlichung, CDN-Verzögerung oder Fallback.
- [ ] Je fünf kontrollierte Kalt-/Warmstarts für Desktop und Mobil mit Startzeit, Profilwechselzeit, Requests, Bytes und Fehlern dokumentieren; mobiler KM1-Start verbessert sich gegenüber dem gemessenen Kandidaten.
- [ ] Auf echtem Smartphone Profilwechsel und Zurücknavigation prüfen.
